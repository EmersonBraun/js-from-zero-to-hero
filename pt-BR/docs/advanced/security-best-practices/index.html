Segurança & Boas Práticas de Performance

Escrever JavaScript correto não é suficiente — código de produção também deve ser seguro, performático e livre de vazamentos de recursos sutis. Este módulo cobre as ameaças de segurança frontend mais impactantes, técnicas práticas de mitigação e os padrões de performance que todo desenvolvedor JavaScript deve internalizar.

1. Cross-Site Scripting (XSS)​

XSS é a vulnerabilidade web mais prevalente. Um atacante injeta scripts maliciosos em uma página que são então executados no navegador de outro usuário, no contexto da sessão da vítima.

Tipos de XSS​

XSS Armazenado — O payload malicioso é armazenado no servidor (por exemplo, em um banco de dados) e servido a todos os visitantes. Um comentário contendo <script>steal(document.cookie)</script> que é salvo e renderizado é o exemplo clássico.

XSS Refletido — O payload é refletido pelo servidor em uma resposta imediata (por exemplo, uma página de resultados de pesquisa que ecoa o parâmetro de query como HTML bruto). O atacante cria uma URL e induz a vítima a clicar nela.

XSS Baseado em DOM — A vulnerabilidade existe inteiramente no JavaScript do lado do cliente. O script lê dados controlados pelo atacante (hash da URL, postMessage, localStorage) e os passa de forma insegura para innerHTML ou outras APIs perigosas.

Prevenção​

  1. Nunca defina innerHTML com dados não confiáveis. Use textContent para texto, createElement + appendChild para construção estruturada do DOM.
  2. Sanitize antes de renderizar HTML. Quando precisar permitir entrada formatada, use uma biblioteca confiável como DOMPurify.
  3. Evite sinks de avaliação perigosos: passar strings do usuário para setTimeout, construção dinâmica de funções, ou atribuição direta ao outerHTML.
  4. Codifique a saída no contexto onde ela aparece (codificação de entidade HTML, codificação de URL, codificação de string JS).
// INSEGURO
element.innerHTML = userInput;

// SEGURO para texto simples
element.textContent = userInput;

// SEGURO para HTML estruturado (com DOMPurify)
element.innerHTML = DOMPurify.sanitize(userInput);

2. CSRF (Cross-Site Request Forgery)​

CSRF explora o anexo automático de cookies pelo navegador. Quando uma vítima visita a página de um atacante, essa página silenciosamente envia uma requisição para um site onde a vítima está autenticada — e o navegador envia o cookie de sessão junto.

Defesas no frontend:

  • Verificar headers Origin / Referer no lado do servidor.
  • Atributo SameSite do cookie: SameSite=Strict ou SameSite=Lax impede que cookies sejam enviados com requisições cross-site.
  • Tokens CSRF: Um valor secreto embutido em formulários e verificado no servidor.
  • Headers de requisição customizados: Requisições fetch com headers como X-Requested-With: XMLHttpRequest não podem ser forjadas por formulários HTML simples (o preflight de CORS as bloqueia para cross-origin).
// Incluindo um token CSRF em requisições fetch
async function securePost(url, data) {
  const csrfToken = document.querySelector('meta[name="csrf-token"]')?.content;
  return fetch(url, {
    method: 'POST',
    credentials: 'same-origin',
    headers: {
      'Content-Type': 'application/json',
      'X-CSRF-Token': csrfToken,
    },
    body: JSON.stringify(data),
  });
}

3. Content Security Policy (CSP)​

CSP é um header de resposta HTTP que diz ao navegador quais origens de recursos são confiáveis. Violações são bloqueadas (e opcionalmente reportadas).

Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.example.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  report-uri /csp-report

Diretivas principais:

DiretivaControla
default-srcFallback para todos os tipos de recursos
script-srcFontes de JavaScript
style-srcFontes de CSS
img-srcFontes de imagens
connect-srcfetch, XHR, WebSocket
frame-ancestorsQuais páginas podem incorporar esta página (substitui X-Frame-Options)

Uma CSP rigorosa bloqueia scripts inline e avaliação dinâmica de código, o que neutraliza a grande maioria dos payloads de XSS mesmo que uma injeção exista.

Referência MDN: Content Security Policy

4. Vazamentos de Memória em JavaScript​

JavaScript usa coleta de lixo — a memória é liberada quando não há mais referências a um objeto. Um vazamento de memória ocorre quando referências são retidas involuntariamente, impedindo o GC de recuperar a memória.

Causas Comuns​

Event listeners esquecidos — Adicionar um listener a um elemento de longa duração de um componente de curta duração sem removê-lo.

// Vazamento: o listener mantém referência à closure/dados mesmo após o componente ser desmontado
window.addEventListener('resize', handler);

// Correção: sempre remover quando não for mais necessário
window.removeEventListener('resize', handler);
// Ou: use AbortController
const controller = new AbortController();
window.addEventListener('resize', handler, { signal: controller.signal });
// Depois:
controller.abort();

Closures retendo objetos grandes — Uma callback de timer que fecha sobre uma grande estrutura de dados a mantém viva enquanto o timer roda.

// Vazamento: largeData é mantido vivo pela closure do interval
let largeData = new Array(1_000_000).fill('x');
const id = setInterval(() => {
  console.log(largeData.length);
}, 1000);
// Correção: clearInterval(id) quando terminar, e definir largeData = null

Nós DOM desanexados — Um elemento DOM é removido do documento mas uma referência JavaScript o mantém (e todos seus filhos) em memória.

// Vazamento
let detachedNode;
function createAndDetach() {
  const el = document.createElement('div');
  document.body.appendChild(el);
  document.body.removeChild(el);
  detachedNode = el; // ainda referenciado!
}
// Correção: definir detachedNode = null quando terminar

Variáveis globais — Atribuição global acidental (sem let/const/var) anexa dados ao window.

function leak() {
  accidentalGlobal = 'still alive'; // global implícito
}
// Correção: modo estrito lança ReferenceError em atribuição não declarada

WeakMap — Use WeakMap para associar dados a objetos sem impedir o GC.

const cache = new WeakMap();

function process(obj) {
  if (cache.has(obj)) return cache.get(obj);
  const result = expensiveCompute(obj);
  cache.set(obj, result); // não impedirá que obj seja coletado pelo GC
  return result;
}

5. Padrão de Event Delegation​

Event delegation anexa um único listener a um elemento pai e trata eventos de muitos filhos via bubbling de evento. Isso é mais performático (menos listeners, sem re-registro para filhos dinâmicos) e evita naturalmente uma categoria de vazamentos de memória.

// Sem delegation — um listener por item
document.querySelectorAll('.item').forEach(item => {
  item.addEventListener('click', handleClick);
});

// Com delegation — um listener, funciona para filhos dinâmicos também
document.getElementById('list').addEventListener('click', (event) => {
  const item = event.target.closest('.item');
  if (!item) return;
  handleClick(item);
});

Benefícios:

  • Funciona para filhos adicionados dinamicamente (sem necessidade de re-registro).
  • Drasticamente menos listeners para listas grandes ou dinâmicas.
  • Uma única chamada removeEventListener para limpar.

Referência MDN: Event delegation

6. Padrão Debounce​

Debounce atrasa a execução até que uma função tenha parado de ser chamada por um período de espera especificado. Se a função for chamada novamente antes do fim da espera, o timer é reiniciado.

Casos de uso: busca enquanto digita, validação de formulário na entrada, tratamento de redimensionamento da janela.

function debounce(fn, wait) {
  let timer;
  return function(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => {
      fn.apply(this, args);
    }, wait);
  };
}

const debouncedSearch = debounce((query) => {
  fetch(`/api/search?q=${encodeURIComponent(query)}`);
}, 300);

searchInput.addEventListener('input', (e) => debouncedSearch(e.target.value));

Debounce de borda inicial — dispara imediatamente na primeira chamada, depois bloqueia até ficar em silêncio:

function debounceLeading(fn, wait) {
  let timer;
  return function(...args) {
    if (!timer) fn.apply(this, args);
    clearTimeout(timer);
    timer = setTimeout(() => { timer = null; }, wait);
  };
}

Referência MDN: setTimeout

7. Padrão Throttle​

Throttle garante que uma função seja chamada no máximo uma vez por intervalo, independentemente de quantas vezes seja disparada. Ao contrário do debounce, garante execução periódica durante atividade sustentada.

Casos de uso: handlers de evento de scroll, rastreamento de movimento do mouse, limitação de chamadas à API.

function throttle(fn, interval) {
  let lastCall = 0;
  return function(...args) {
    const now = Date.now();
    if (now - lastCall >= interval) {
      lastCall = now;
      return fn.apply(this, args);
    }
  };
}

const throttledScroll = throttle(() => {
  updateScrollProgress();
}, 100); // no máximo 10 vezes por segundo

window.addEventListener('scroll', throttledScroll);

8. Sanitização de Entrada​

Nunca confie na entrada do usuário. Sanitize em cada fronteira.

// Codificação de entidade HTML — seguro para inserir texto em contextos HTML
function escapeHTML(str) {
  return String(str)
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#x27;');
}

// Sanitização de parâmetros de URL
function buildSearchURL(query) {
  const url = new URL('https://example.com/search');
  url.searchParams.set('q', query); // A API de URL trata da codificação
  return url.toString();
}

// Validação de entrada numérica
function sanitizeAge(input) {
  const n = parseInt(input, 10);
  if (Number.isNaN(n) || n < 0 || n > 150) return null;
  return n;
}

Regras principais:

  • Sanitize no ponto de uso, não apenas na entrada.
  • Use a codificação correta para o contexto (HTML, URL, JSON, SQL — cada um é diferente).
  • Prefira APIs estruturadas (URLSearchParams, JSON.stringify) em vez de construção manual de strings.
  • Use allowlist de valores válidos quando possível em vez de tentar fazer blocklist de inválidos.

9. Práticas de Codificação Segura​

Evite execução dinâmica de código — Passar strings controladas pelo usuário para setTimeout, setInterval, ou outros mecanismos de avaliação dinâmica executa código arbitrário e contorna todas as proteções de CSP e análise estática. Use funções callback em vez de argumentos de string.

Use modo estrito — Captura variáveis não declaradas, impede coerção de this, e desabilita recursos legados perigosos.

Valide a forma dos dados — Ao consumir dados externos (APIs, postMessage, localStorage), valide a estrutura antes do uso.

window.addEventListener('message', (event) => {
  // Sempre verifique a origem
  if (event.origin !== 'https://trusted.example.com') return;

  // Valide a forma
  const { type, payload } = event.data ?? {};
  if (typeof type !== 'string' || !payload) return;

  handleMessage(type, payload);
});

Subresource Integrity (SRI) — Verifique que scripts de terceiros não foram adulterados:

<script
  src="https://cdn.example.com/lib.js"
  integrity="sha384-<hash>"
  crossorigin="anonymous"
></script>

Evite armazenar dados sensíveis em localStorage — Ele é acessível a qualquer JavaScript na página. Prefira cookies HttpOnly para tokens de sessão.

Resumo​

  • XSS é prevenido evitando sinks inseguros (innerHTML, execução dinâmica de código), sanitizando HTML não confiável com DOMPurify, e usando textContent para saída de texto simples.
  • CSRF é mitigado por cookies SameSite, tokens CSRF e verificação de origens de requisição no servidor.
  • Content Security Policy é uma allowlist declarativa que bloqueia fontes de script não autorizadas e neutraliza a maioria dos payloads de XSS no nível do navegador.
  • Vazamentos de memória surgem de event listeners esquecidos, closures de timer, nós DOM desanexados e globais acidentais. Use removeEventListener, AbortController, clearInterval e WeakMap para preveni-los.
  • Event delegation anexa um listener ao pai em vez de muitos listeners aos filhos — mais performático e inerentemente correto para conteúdo dinâmico.
  • Debounce atrasa a execução até que a atividade pare; throttle limita a taxa de execução durante atividade sustentada. Ambos são essenciais para handlers de eventos de alta frequência.
  • Sanitização de entrada deve ser sensível ao contexto: codificação de entidade HTML, codificação de URL e validação estrutural servem a propósitos diferentes e não são intercambiáveis.
  • Codificação segura significa validar origens de postMessage, evitar avaliação dinâmica de código com entrada do usuário, usar modo estrito, preferir cookies HttpOnly para tokens e aplicar Subresource Integrity para scripts de terceiros.
