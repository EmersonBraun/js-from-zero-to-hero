Seguridad y Mejores Prácticas de Rendimiento

Escribir JavaScript correcto no es suficiente — el código de producción también debe ser seguro, eficiente y libre de fugas de recursos sutiles. Este módulo cubre las amenazas de seguridad frontend más impactantes, técnicas prácticas de mitigación y los patrones de rendimiento que todo desarrollador JavaScript debe interiorizar.

1. Cross-Site Scripting (XSS)​

XSS es la vulnerabilidad web más prevalente. Un atacante inyecta scripts maliciosos en una página que luego se ejecutan en el navegador de otro usuario, en el contexto de la sesión de la víctima.

Tipos de XSS​

XSS Almacenado — El payload malicioso se almacena en el servidor (ej.: en una base de datos) y se sirve a todos los visitantes. Un comentario que contiene alert de script que se guarda y renderiza es el ejemplo clásico.

XSS Reflejado — El payload se refleja desde el servidor en una respuesta inmediata (ej.: una página de resultados de búsqueda que hace eco del parámetro de consulta como HTML crudo). El atacante crea una URL y engaña a la víctima para que haga clic.

XSS Basado en DOM — La vulnerabilidad vive completamente en el JavaScript del lado del cliente. El script lee datos controlados por el atacante (hash de URL, postMessage, localStorage) y los pasa de forma insegura a innerHTML.

Prevención​

  1. Nunca establezcas innerHTML con datos no confiables. Usa textContent para texto, createElement + appendChild para construcción DOM estructurada.
  2. Sanitiza antes de renderizar HTML. Cuando debes permitir entrada formateada, usa una biblioteca confiable como DOMPurify.
  3. Evita sumideros de evaluación peligrosos: pasar cadenas de usuario a setTimeout con strings, construcción dinámica de funciones, o element.outerHTML.
  4. Codifica la salida en el contexto donde aparece (codificación de entidades HTML, codificación URL, codificación de cadenas JS).
// INSEGURO
element.innerHTML = userInput;

// SEGURO para texto plano
element.textContent = userInput;

// SEGURO para HTML estructurado (con DOMPurify)
element.innerHTML = DOMPurify.sanitize(userInput);

2. CSRF (Cross-Site Request Forgery)​

CSRF explota el adjunto automático de cookies del navegador. Cuando una víctima visita la página de un atacante, esa página envía silenciosamente una solicitud a un sitio donde la víctima está autenticada — y el navegador envía su cookie de sesión junto con ella.

Defensas del frontend:

  • Verificar headers Origin / Referer del lado del servidor.
  • Atributo SameSite de cookie: SameSite=Strict o SameSite=Lax evita que las cookies se envíen con solicitudes entre sitios.
  • Tokens CSRF: Un valor secreto incrustado en formularios y verificado del lado del servidor.
  • Headers de solicitud personalizados: Las solicitudes fetch con headers como X-Requested-With: XMLHttpRequest no pueden ser falsificadas por formularios HTML simples (CORS preflight los bloquea para origenes cruzados).
// Incluir un token CSRF en solicitudes fetch
async function securePost(url, data) {
  const csrfToken = document.querySelector('meta[name="csrf-token"]')?.content;
  return fetch(url, {
    method: 'POST',
    credentials: 'same-origin',
    headers: {
      'Content-Type': 'application/json',
      'X-CSRF-Token': csrfToken,
    },
    body: JSON.stringify(data),
  });
}

3. Content Security Policy (CSP)​

CSP es un header de respuesta HTTP que le dice al navegador qué orígenes de recursos son confiables. Las violaciones son bloqueadas (y opcionalmente reportadas).

Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.example.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  report-uri /csp-report

Directivas clave:

DirectivaControla
default-srcRespaldo para todos los tipos de recursos
script-srcFuentes de JavaScript
style-srcFuentes de CSS
img-srcFuentes de imágenes
connect-srcfetch, XHR, WebSocket
frame-ancestorsQué páginas pueden incrustar esta página (reemplaza X-Frame-Options)

Un CSP estricto bloquea scripts inline y evaluación dinámica de código, lo que neutraliza la gran mayoría de los payloads XSS incluso si existe una inyección.

4. Fugas de Memoria en JavaScript​

JavaScript usa recolección de basura — la memoria se libera cuando no hay más referencias a un objeto. Una fuga de memoria ocurre cuando las referencias se retienen sin intención, evitando que el GC reclame memoria.

Causas Comunes​

Event listeners olvidados — Agregar un listener a un elemento de larga duración desde un componente de corta duración sin eliminarlo.

// Fuga: el listener retiene una referencia al closure/datos incluso después de desmontar el componente
window.addEventListener('resize', handler);

// Corrección: siempre eliminar cuando ya no sea necesario
window.removeEventListener('resize', handler);
// O: usar AbortController
const controller = new AbortController();
window.addEventListener('resize', handler, { signal: controller.signal });
// Más tarde:
controller.abort();

Closures que retienen objetos grandes — Un callback de temporizador que cierra sobre una estructura de datos grande la mantiene viva mientras el temporizador se ejecuta.

// Fuga: largeData se mantiene viva por el closure del intervalo
let largeData = new Array(1_000_000).fill('x');
const id = setInterval(() => {
  console.log(largeData.length);
}, 1000);
// Corrección: clearInterval(id) cuando termine, y establecer largeData = null

Nodos DOM desconectados — Un elemento DOM se elimina del documento pero una referencia JavaScript lo mantiene (y todos sus hijos) en memoria.

// Fuga
let detachedNode;
function createAndDetach() {
  const el = document.createElement('div');
  document.body.appendChild(el);
  document.body.removeChild(el);
  detachedNode = el; // ¡todavía referenciado!
}
// Corrección: establecer detachedNode = null cuando termine

Variables globales — La asignación global accidental (falta let/const/var) adjunta datos a window.

function leak() {
  accidentalGlobal = 'still alive'; // global implícita
}
// Corrección: el modo estricto lanza ReferenceError en asignación no declarada

WeakMap — Usa WeakMap para asociar datos con objetos sin evitar el GC.

const cache = new WeakMap();

function process(obj) {
  if (cache.has(obj)) return cache.get(obj);
  const result = expensiveCompute(obj);
  cache.set(obj, result); // no evitará que obj sea recolectado
  return result;
}

5. Patrón de Delegación de Eventos​

La delegación de eventos adjunta un único listener a un elemento padre y maneja eventos de muchos hijos a través de la propagación de eventos. Esto es más eficiente (menos listeners, sin re-registro para hijos dinámicos) y evita naturalmente una categoría de fugas de memoria.

// Sin delegación — un listener por elemento
document.querySelectorAll('.item').forEach(item => {
  item.addEventListener('click', handleClick);
});

// Con delegación — un listener, funciona también para hijos dinámicos
document.getElementById('list').addEventListener('click', (event) => {
  const item = event.target.closest('.item');
  if (!item) return;
  handleClick(item);
});

Beneficios:

  • Funciona para hijos añadidos dinámicamente (sin re-registro necesario).
  • Drásticamente menos listeners para listas grandes o dinámicas.
  • Una sola llamada removeEventListener para limpiar.

Referencia MDN: Event delegation

6. Patrón Debounce​

Debounce retrasa la ejecución hasta que una función ha dejado de ser llamada durante un período de espera especificado. Si la función se llama de nuevo antes de que expire la espera, el temporizador se reinicia.

Casos de uso: búsqueda mientras se escribe, validación de formularios en input, manejo del resize de ventana.

function debounce(fn, wait) {
  let timer;
  return function(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => {
      fn.apply(this, args);
    }, wait);
  };
}

const debouncedSearch = debounce((query) => {
  fetch(`/api/search?q=${encodeURIComponent(query)}`);
}, 300);

searchInput.addEventListener('input', (e) => debouncedSearch(e.target.value));

Debounce de borde inicial — se dispara inmediatamente en la primera llamada, luego bloquea hasta que haya silencio:

function debounceLeading(fn, wait) {
  let timer;
  return function(...args) {
    if (!timer) fn.apply(this, args);
    clearTimeout(timer);
    timer = setTimeout(() => { timer = null; }, wait);
  };
}

Referencia MDN: setTimeout

7. Patrón Throttle​

Throttle asegura que una función se llame como máximo una vez por intervalo, independientemente de cuántas veces se dispare. A diferencia de debounce, garantiza ejecución periódica durante actividad sostenida.

Casos de uso: handlers de eventos scroll, seguimiento del movimiento del mouse, limitación de llamadas a API.

function throttle(fn, interval) {
  let lastCall = 0;
  return function(...args) {
    const now = Date.now();
    if (now - lastCall >= interval) {
      lastCall = now;
      return fn.apply(this, args);
    }
  };
}

const throttledScroll = throttle(() => {
  updateScrollProgress();
}, 100); // como máximo 10 veces por segundo

window.addEventListener('scroll', throttledScroll);
PatrónSe dispara cuandoMejor para
DebounceLa actividad se detieneEntrada de búsqueda, finalización de resize
ThrottleA intervalos regularesScroll, mousemove, game loops

8. Sanitización de Entrada​

Nunca confíes en la entrada del usuario. Sanitiza en cada límite.

// Codificación de entidades HTML — segura para insertar texto en contextos HTML
function escapeHTML(str) {
  return String(str)
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#x27;');
}

// Sanitización de parámetros URL
function buildSearchURL(query) {
  const url = new URL('https://example.com/search');
  url.searchParams.set('q', query); // la API URL maneja la codificación
  return url.toString();
}

// Validación de entrada numérica
function sanitizeAge(input) {
  const n = parseInt(input, 10);
  if (Number.isNaN(n) || n < 0 || n > 150) return null;
  return n;
}

Reglas clave:

  • Sanitiza en el punto de uso, no solo en la entrada.
  • Usa la codificación correcta para el contexto (HTML, URL, JSON — cada uno es diferente).
  • Prefiere APIs estructuradas (URLSearchParams, JSON.stringify) sobre construcción manual de cadenas.
  • Usa listas de permitidos de valores válidos cuando sea posible en lugar de intentar bloquear los inválidos.

9. Prácticas de Codificación Segura​

Evita la ejecución dinámica de código — Pasar cadenas controladas por el usuario a mecanismos de evaluación dinámica ejecuta código arbitrario y evita todas las protecciones de CSP y análisis estático. Usa funciones callback en lugar de argumentos de cadena.

Usa modo estricto — Detecta variables no declaradas, previene la coerción de this y desactiva características heredadas peligrosas.

Valida la forma de los datos — Al consumir datos externos (APIs, postMessage, localStorage), valida la estructura antes de usar.

window.addEventListener('message', (event) => {
  // Siempre verificar el origen
  if (event.origin !== 'https://trusted.example.com') return;

  // Validar forma
  const { type, payload } = event.data ?? {};
  if (typeof type !== 'string' || !payload) return;

  handleMessage(type, payload);
});

Integridad de Subrecurso (SRI) — Verifica que los scripts de terceros no hayan sido manipulados:

<script
  src="https://cdn.example.com/lib.js"
  integrity="sha384-<hash>"
  crossorigin="anonymous"
></script>

Evita almacenar datos sensibles en localStorage — Es accesible para cualquier JavaScript en la página. Prefiere cookies HttpOnly para tokens de sesión.

Resumen​

  • XSS se previene evitando sumideros inseguros (innerHTML, ejecución dinámica de código), sanitizando HTML no confiable con DOMPurify y usando textContent para salida de texto plano.
  • CSRF se mitiga con cookies SameSite, tokens CSRF y verificando los orígenes de las solicitudes del lado del servidor.
  • Content Security Policy es una lista de permitidos declarativa que bloquea fuentes de scripts no autorizadas y neutraliza la mayoría de los payloads XSS a nivel del navegador.
  • Las fugas de memoria surgen de event listeners olvidados, closures de temporizadores, nodos DOM desconectados y globales accidentales. Usa removeEventListener, AbortController, clearInterval y WeakMap para prevenirlas.
  • La delegación de eventos adjunta un listener a un padre en lugar de muchos listeners a los hijos — más eficiente e intrínsecamente correcto para contenido dinámico.
  • Debounce retrasa la ejecución hasta que la actividad se detiene; throttle limita la tasa de ejecución durante actividad sostenida. Ambos son esenciales para handlers de eventos de alta frecuencia.
  • La sanitización de entrada debe ser consciente del contexto: la codificación de entidades HTML, la codificación URL y la validación estructural sirven propósitos diferentes y no son intercambiables.
  • La codificación segura significa validar orígenes de postMessage, evitar la evaluación dinámica de código con entrada del usuario, usar modo estricto, preferir cookies HttpOnly para tokens y aplicar Integridad de Subrecurso para scripts de terceros.
