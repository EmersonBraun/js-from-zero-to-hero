Async JavaScript

JavaScript Is Single-Threaded​

JavaScript has a single call stack. That means it can only do one thing at a time — it processes one expression, one function call, one line of code at a time, in sequence. There is no parallel execution of JavaScript code in a single thread.

This raises an obvious question: how can a web browser download a file, animate a spinner, and respond to user input all at the same time?

The answer is the Event Loop — one of the most important mechanisms in the entire JavaScript runtime. Understanding it deeply will make you a significantly better JavaScript developer.

"JavaScript has a concurrency model based on an event loop, which is responsible for executing the code, collecting and processing events, and executing queued sub-tasks."

— MDN: Event Loop

The Call Stack​

The call stack is a LIFO (last-in, first-out) data structure that tracks the current execution context. Every time a function is called, a new frame is pushed onto the stack. When the function returns, its frame is popped off.

function c() { console.log("c"); }
function b() { c(); }
function a() { b(); }

a();

Call stack progression:

[a]          → a calls b
[b, a]       → b calls c
[c, b, a]    → c calls console.log
[b, a]       → c returns
[a]          → b returns
[]           → a returns

When the stack is empty, the runtime is idle and the Event Loop can pick up the next task.

Further reading: MDN: Call stack

Web APIs and the Browser Environment​

JavaScript itself does not know how to do I/O, timers, or network requests. These capabilities are provided by the browser (or Node.js runtime) as Web APIs:

  • setTimeout / setInterval
  • fetch
  • DOM event listeners
  • XMLHttpRequest
  • requestAnimationFrame

When you call setTimeout(callback, 1000), you are handing the callback to the browser's timer API. The browser runs a timer in a separate thread (outside the JS engine). After 1000ms, the browser places the callback into the callback queue. The JS thread never blocks.

The Callback Queue and Microtask Queue​

There are two queues that feed tasks back to the JS engine:

Callback Queue (Task Queue / Macrotask Queue)​

Holds callbacks scheduled by:

  • setTimeout / setInterval
  • DOM events (click, input, etc.)
  • setImmediate (Node.js)
  • I/O callbacks

Microtask Queue​

Holds callbacks scheduled by:

  • Promise .then / .catch / .finally callbacks
  • queueMicrotask()
  • MutationObserver callbacks
  • async/await continuations

Critical difference: The microtask queue is always fully drained before the Event Loop picks the next macrotask. Microtasks have higher priority.

Further reading: MDN: Microtask guide

The Event Loop — Step by Step​

The Event Loop can be described by this pseudo-algorithm:

while (true) {
  if (callStack is empty) {
    drain entire microtask queue (run all microtasks)
    if (callbackQueue is not empty) {
      pick ONE callback from callbackQueue
      push it onto callStack
      run it to completion
    }
  }
}

A Famous Interview Question​

console.log("1");

setTimeout(() => console.log("2"), 0);

Promise.resolve().then(() => console.log("3"));

console.log("4");

Output order: 1, 4, 3, 2

  • 1 and 4 are synchronous → run immediately on call stack
  • The Promise .then callback → goes to the microtask queue
  • The setTimeout callback (even with 0ms!) → goes to the callback queue (macrotask)
  • After synchronous code finishes, Event Loop drains microtasks → 3
  • Then picks one macrotask → 2

Callbacks and Callback Hell​

Before Promises, asynchronous operations were coordinated using callbacks. When multiple async operations depend on each other, the code becomes deeply nested — a pattern called callback hell or the pyramid of doom:

getUser(userId, function (err, user) {
  if (err) return handleError(err);

  getOrders(user.id, function (err, orders) {
    if (err) return handleError(err);

    getOrderDetails(orders[0].id, function (err, details) {
      if (err) return handleError(err);

      getShipping(details.shippingId, function (err, shipping) {
        if (err) return handleError(err);

        // Finally do something...
        console.log(shipping);
      });
    });
  });
});

Problems with callback hell:

  • Hard to read and reason about
  • Error handling is repetitive and easy to miss
  • Control flow is inverted (you hand control to the callback)
  • Very difficult to compose or reuse

Promises were introduced to solve this.

Promises​

A Promise is an object representing the eventual completion (or failure) of an asynchronous operation and its resulting value.

A Promise is always in one of three states:

  • Pending: initial state, operation in progress
  • Fulfilled: operation completed successfully, has a value
  • Rejected: operation failed, has a reason (error)

Once settled (fulfilled or rejected), a Promise cannot change state. It is immutable.

Further reading: MDN: Promise

Creating a Promise​

const myPromise = new Promise((resolve, reject) => {
  // Executor function: runs synchronously
  const success = true;

  if (success) {
    resolve("Operation succeeded!"); // fulfill with a value
  } else {
    reject(new Error("Operation failed!")); // reject with an error
  }
});

.then, .catch, .finally​

myPromise
  .then((value) => {
    console.log(value); // "Operation succeeded!"
    return value.toUpperCase(); // return value passes to next .then
  })
  .then((upper) => {
    console.log(upper); // "OPERATION SUCCEEDED!"
  })
  .catch((error) => {
    console.error(error.message); // handles any rejection in the chain
  })
  .finally(() => {
    console.log("Always runs, regardless of outcome");
  });

.then always returns a new Promise, which enables chaining.

Further reading: MDN: Promise.prototype.then

Promise Chaining​

Promise chaining transforms the callback hell example into flat, readable code:

getUser(userId)
  .then((user) => getOrders(user.id))
  .then((orders) => getOrderDetails(orders[0].id))
  .then((details) => getShipping(details.shippingId))
  .then((shipping) => console.log(shipping))
  .catch((err) => handleError(err)); // one handler catches any error in the chain

How chaining works internally​

When .then(handler) is called:

  1. A new Promise is returned.
  2. If handler returns a plain value, the new Promise fulfills with that value.
  3. If handler returns a Promise, the new Promise "adopts" that Promise's state.
  4. If handler throws, the new Promise rejects.

Promise Combinators​

For running multiple async operations simultaneously or racing them:

Promise.all — All or Nothing​

Resolves when all promises fulfill; rejects immediately if any rejects.

const [users, products, orders] = await Promise.all([
  fetch("/api/users").then((r) => r.json()),
  fetch("/api/products").then((r) => r.json()),
  fetch("/api/orders").then((r) => r.json()),
]);

Further reading: MDN: Promise.all

Promise.race — First to Settle​

Resolves or rejects with the value of the first promise to settle (either direction):

const result = await Promise.race([
  fetch("/api/data"),
  new Promise((_, reject) => setTimeout(() => reject(new Error("Timeout")), 5000)),
]);

This pattern is useful for implementing timeouts.

Further reading: MDN: Promise.race

Promise.allSettled — Wait for All, Regardless​

Resolves when all promises settle (either fulfilled or rejected). Never rejects. Each result has { status: 'fulfilled', value } or { status: 'rejected', reason }:

const results = await Promise.allSettled([
  Promise.resolve("ok"),
  Promise.reject("fail"),
  Promise.resolve("also ok"),
]);

results.forEach(({ status, value, reason }) => {
  if (status === "fulfilled") console.log("Success:", value);
  else console.log("Failed:", reason);
});

Further reading: MDN: Promise.allSettled

Promise.any — First to Fulfill​

Resolves with the first fulfilled value. Only rejects if all promises reject (throws AggregateError):

const fastest = await Promise.any([
  fetch("https://server1.example.com/data"),
  fetch("https://server2.example.com/data"),
  fetch("https://server3.example.com/data"),
]);

Further reading: MDN: Promise.any

async / await​

The async/await syntax is syntactic sugar over Promises. It lets you write asynchronous code that reads like synchronous code. Under the hood, an async function returns a Promise, and await suspends execution of the function until the awaited Promise settles.

// Promise style:
function loadUserData(id) {
  return fetch(`/api/users/${id}`)
    .then((res) => {
      if (!res.ok) throw new Error("Not found");
      return res.json();
    })
    .then((user) => fetch(`/api/orders?userId=${user.id}`))
    .then((res) => res.json());
}

// Equivalent async/await style:
async function loadUserData(id) {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) throw new Error("Not found");
  const user = await res.json();
  const ordersRes = await fetch(`/api/orders?userId=${user.id}`);
  return ordersRes.json();
}

Rules of async/await:

  • async always makes a function return a Promise
  • await can only be used inside async functions (or at the top level of ES modules)
  • await pauses only the current async function — the rest of the JavaScript runtime keeps running
  • If the awaited Promise rejects, await throws the rejection reason

Further reading: MDN: async function

Error Handling with try/catch​

With async/await, the idiomatic error handling approach is try/catch:

async function fetchUserProfile(username) {
  try {
    const res = await fetch(`https://api.github.com/users/${username}`);

    if (!res.ok) {
      throw new Error(`HTTP error! Status: ${res.status}`);
    }

    const data = await res.json();
    return data;
  } catch (error) {
    if (error.name === "TypeError") {
      console.error("Network failure or CORS issue:", error.message);
    } else {
      console.error("API error:", error.message);
    }
    throw error; // re-throw if caller needs to handle it too
  } finally {
    console.log("Fetch attempt complete");
  }
}

Handling Errors Without try/catch​

An alternative pattern that avoids try/catch nesting:

async function safeAsync(promise) {
  try {
    const data = await promise;
    return [null, data];
  } catch (error) {
    return [error, null];
  }
}

const [err, user] = await safeAsync(fetchUserProfile("octocat"));
if (err) {
  console.error("Failed:", err.message);
} else {
  console.log("User:", user.login);
}

The Fetch API​

fetch is the modern, Promise-based API for making HTTP requests from the browser:

// GET request
const response = await fetch("https://api.github.com/users/octocat");
const user = await response.json();

// POST request
const response = await fetch("https://api.example.com/items", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Authorization": `Bearer ${token}`,
  },
  body: JSON.stringify({ name: "New Item", price: 9.99 }),
});

if (!response.ok) {
  throw new Error(`HTTP ${response.status}: ${response.statusText}`);
}

const newItem = await response.json();

Important: fetch only rejects on network failures (no connection, CORS blocked). A 404 or 500 response still resolves — you must check response.ok or response.status manually.

Project: GitHub Profiles​

This project fetches real user data from the GitHub API and renders a profile card. It demonstrates async/await, error handling, and the Fetch API in a real-world context.

Challenge 1​

Add a loading state: show a spinner while the fetch is in progress and hide it when complete (success or failure). Use a finally block.

Challenge 2​

Add search history: store the last 5 searched usernames in localStorage and display them as clickable chips. Clicking a chip re-fetches that user's profile.

Project: Pokédex​

Fetches Pokémon data from the PokéAPI and displays a searchable list. Uses Promise.all to fetch data for multiple Pokémon simultaneously.

Challenge 1​

Implement infinite scroll: as the user scrolls to the bottom of the list, fetch the next batch of Pokémon using the PokéAPI's limit and offset query parameters.

Project: URL Shortener​

Uses a third-party API to shorten URLs. Demonstrates POST requests with fetch, JSON serialization, and clipboard API.

Challenge 1​

Add URL validation before making the API call. Use a regex or the URL constructor to check if the input is a valid URL. Show an inline error message for invalid input.

Challenge 2​

Store the history of shortened URLs in localStorage and render a history panel. Add a button to clear the history.

Project: QR Code Generator​

Generates QR codes from user input using an external API. Demonstrates dynamic image loading and async error handling.

Challenge 1​

Add a debounced live preview: generate the QR code automatically as the user types, with a 500ms debounce to avoid excessive API calls. (Combine closures + async!)

Challenge 2​

Add a download button that lets users save the QR code as a PNG file. Use fetch to get the image as a blob, then create a temporary download link.

Project: Random Image Feed​

Fetches images from a public API (e.g., Unsplash) and renders an infinite scrolling image gallery. Uses Promise.allSettled to gracefully handle any failed image loads.

Challenge 1​

Implement category filtering: add a row of filter buttons (nature, animals, architecture, etc.) that refetch images with the selected category query parameter. Show a loading skeleton while fetching.

Summary​

  • JavaScript is single-threaded: one call stack, one operation at a time.
  • The browser environment provides Web APIs (timers, fetch, events) that operate outside the JS engine.
  • The Event Loop coordinates the call stack with two queues: the macrotask queue and the microtask queue (which is always drained first and holds Promise callbacks).
  • Callbacks were the original async pattern but lead to deeply nested, hard-to-maintain code.
  • A Promise is an object representing a future value. It is always in one of three states: pending, fulfilled, or rejected. Once settled, it is immutable.
  • Promise chaining flattens async code by returning values (or new Promises) from .then handlers.
  • Promise combinators: Promise.all (all or nothing), Promise.race (first to settle), Promise.allSettled (all, regardless), Promise.any (first to fulfill).
  • async/await is syntactic sugar over Promises, making async code read like synchronous code.
  • Use try/catch/finally with async/await for clean error handling.
  • The Fetch API is Promise-based; check response.ok explicitly since 4xx/5xx responses do not cause fetch to reject.
