# JavaScript Assíncrono

## JavaScript É Single-Threaded

JavaScript possui uma **única pilha de chamadas**. Isso significa que ele pode fazer apenas uma coisa de cada vez — processa uma expressão, uma chamada de função, uma linha de código de cada vez, em sequência. Não há execução paralela de código JavaScript em uma única thread.

Isso levanta uma questão óbvia: como um navegador web pode baixar um arquivo, animar um spinner e responder à entrada do usuário ao mesmo tempo?

A resposta é o **Event Loop** — um dos mecanismos mais importantes em todo o runtime JavaScript. Entendê-lo profundamente vai tornar você um desenvolvedor JavaScript significativamente melhor.

> "JavaScript tem um modelo de concorrência baseado em um event loop, que é responsável por executar o código, coletar e processar eventos, e executar subtarefas enfileiradas."
>
> — [MDN: Event Loop](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Event_loop)

---

## A Pilha de Chamadas

A **pilha de chamadas** é uma estrutura de dados LIFO (último a entrar, primeiro a sair) que rastreia o contexto de execução atual. Toda vez que uma função é chamada, um novo frame é empurrado para a pilha. Quando a função retorna, seu frame é retirado.

```js
function c() { console.log("c"); }
function b() { c(); }
function a() { b(); }

a();
```

Progressão da pilha de chamadas:

```
[a]          → a chama b
[b, a]       → b chama c
[c, b, a]    → c chama console.log
[b, a]       → c retorna
[a]          → b retorna
[]           → a retorna
```

Quando a pilha está vazia, o runtime está ocioso e o Event Loop pode pegar a próxima tarefa.

> Leitura adicional: [MDN: Call stack](https://developer.mozilla.org/en-US/docs/Glossary/Call_stack)

---

## Web APIs e o Ambiente do Navegador

JavaScript por si só não sabe como fazer I/O, timers ou requisições de rede. Essas capacidades são fornecidas pelo **navegador** (ou runtime Node.js) como **Web APIs**:

- `setTimeout` / `setInterval`
- `fetch`
- Listeners de eventos DOM
- `XMLHttpRequest`
- `requestAnimationFrame`

Quando você chama `setTimeout(callback, 1000)`, você está entregando o callback à API de timer do navegador. O navegador executa um timer em uma thread separada (fora do motor JS). Após 1000ms, o navegador coloca o callback na **fila de callbacks**. A thread JS nunca bloqueia.

---

## A Fila de Callbacks e a Fila de Microtarefas

Existem duas filas que alimentam tarefas de volta ao motor JS:

### Fila de Callbacks (Fila de Tarefas / Fila de Macrotarefas)

Contém callbacks agendados por:
- `setTimeout` / `setInterval`
- Eventos DOM (`click`, `input`, etc.)
- `setImmediate` (Node.js)
- Callbacks de I/O

### Fila de Microtarefas

Contém callbacks agendados por:
- Callbacks de **Promise `.then` / `.catch` / `.finally`**
- `queueMicrotask()`
- Callbacks de `MutationObserver`
- Continuações de `async/await`

**Diferença crítica:** A fila de microtarefas é **sempre completamente drenada** antes de o Event Loop pegar a próxima macrotarefa. Microtarefas têm prioridade maior.

> Leitura adicional: [MDN: Microtask guide](https://developer.mozilla.org/en-US/docs/Web/API/HTML_DOM_API/Microtask_guide)

---

## O Event Loop — Passo a Passo

O Event Loop pode ser descrito por este pseudoalgoritmo:

```
while (true) {
  if (callStack is empty) {
    drain entire microtask queue (run all microtasks)
    if (callbackQueue is not empty) {
      pick ONE callback from callbackQueue
      push it onto callStack
      run it to completion
    }
  }
}
```

### Uma Famosa Pergunta de Entrevista

```js
console.log("1");

setTimeout(() => console.log("2"), 0);

Promise.resolve().then(() => console.log("3"));

console.log("4");
```

Ordem de saída: `1`, `4`, `3`, `2`

- `1` e `4` são síncronos → executam imediatamente na pilha de chamadas
- O callback `.then` da Promise → vai para a **fila de microtarefas**
- O callback do `setTimeout` (mesmo com 0ms!) → vai para a **fila de callbacks** (macrotarefa)
- Após o código síncrono terminar, o Event Loop drena microtarefas → `3`
- Então pega uma macrotarefa → `2`

## Callbacks e Callback Hell

Antes das Promises, operações assíncronas eram coordenadas usando callbacks. Quando múltiplas operações assíncronas dependem umas das outras, o código fica profundamente aninhado — um padrão chamado de **callback hell** ou **pirâmide da perdição**:

```js
getUser(userId, function (err, user) {
  if (err) return handleError(err);

  getOrders(user.id, function (err, orders) {
    if (err) return handleError(err);

    getOrderDetails(orders[0].id, function (err, details) {
      if (err) return handleError(err);

      getShipping(details.shippingId, function (err, shipping) {
        if (err) return handleError(err);

        // Finalmente fazer algo...
        console.log(shipping);
      });
    });
  });
});
```

Problemas com callback hell:
- Difícil de ler e raciocinar
- Tratamento de erros é repetitivo e fácil de esquecer
- O fluxo de controle é invertido (você entrega o controle ao callback)
- Muito difícil de compor ou reutilizar

As Promises foram introduzidas para resolver isso.

## Promises

Uma **Promise** é um objeto que representa a eventual conclusão (ou falha) de uma operação assíncrona e seu valor resultante.

Uma Promise está sempre em um de três estados:
- **Pendente**: estado inicial, operação em andamento
- **Cumprida**: operação concluída com sucesso, tem um valor
- **Rejeitada**: operação falhou, tem um motivo (erro)

Uma vez resolvida (cumprida ou rejeitada), uma Promise **não pode mudar de estado**. Ela é imutável.

> Leitura adicional: [MDN: Promise](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise)

### Criando uma Promise

```js
const myPromise = new Promise((resolve, reject) => {
  // Função executor: executa de forma síncrona
  const success = true;

  if (success) {
    resolve("Operation succeeded!"); // cumprir com um valor
  } else {
    reject(new Error("Operation failed!")); // rejeitar com um erro
  }
});
```

### `.then`, `.catch`, `.finally`

```js
myPromise
  .then((value) => {
    console.log(value); // "Operation succeeded!"
    return value.toUpperCase(); // valor retornado passa para o próximo .then
  })
  .then((upper) => {
    console.log(upper); // "OPERATION SUCCEEDED!"
  })
  .catch((error) => {
    console.error(error.message); // trata qualquer rejeição na cadeia
  })
  .finally(() => {
    console.log("Always runs, regardless of outcome");
  });
```

`.then` sempre retorna uma nova Promise, o que permite o **encadeamento**.

> Leitura adicional: [MDN: Promise.prototype.then](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/then)

---

## Encadeamento de Promises

O encadeamento de Promises transforma o exemplo de callback hell em código plano e legível:

```js
getUser(userId)
  .then((user) => getOrders(user.id))
  .then((orders) => getOrderDetails(orders[0].id))
  .then((details) => getShipping(details.shippingId))
  .then((shipping) => console.log(shipping))
  .catch((err) => handleError(err)); // um handler captura qualquer erro na cadeia
```

### Como o Encadeamento Funciona Internamente

Quando `.then(handler)` é chamado:
1. Uma nova Promise é retornada.
2. Se `handler` retorna um valor simples, a nova Promise se cumpre com esse valor.
3. Se `handler` retorna uma Promise, a nova Promise "adota" o estado dessa Promise.
4. Se `handler` lança uma exceção, a nova Promise é rejeitada.

## Combinadores de Promise

Para executar múltiplas operações assíncronas simultaneamente ou em corrida:

### `Promise.all` — Tudo ou Nada

Resolve quando **todas** as promises se cumprem; rejeita imediatamente se **qualquer uma** rejeitar.

```js
const [users, products, orders] = await Promise.all([
  fetch("/api/users").then((r) => r.json()),
  fetch("/api/products").then((r) => r.json()),
  fetch("/api/orders").then((r) => r.json()),
]);
```

> Leitura adicional: [MDN: Promise.all](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/all)

### `Promise.race` — Primeiro a Resolver

Resolve ou rejeita com o valor da **primeira promise a se resolver** (em qualquer direção):

```js
const result = await Promise.race([
  fetch("/api/data"),
  new Promise((_, reject) => setTimeout(() => reject(new Error("Timeout")), 5000)),
]);
```

Esse padrão é útil para implementar timeouts.

> Leitura adicional: [MDN: Promise.race](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/race)

### `Promise.allSettled` — Esperar por Todas, Independente

Resolve quando **todas** as promises se resolvem (cumpridas ou rejeitadas). Nunca rejeita. Cada resultado tem `{ status: 'fulfilled', value }` ou `{ status: 'rejected', reason }`:

```js
const results = await Promise.allSettled([
  Promise.resolve("ok"),
  Promise.reject("fail"),
  Promise.resolve("also ok"),
]);

results.forEach(({ status, value, reason }) => {
  if (status === "fulfilled") console.log("Success:", value);
  else console.log("Failed:", reason);
});
```

> Leitura adicional: [MDN: Promise.allSettled](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/allSettled)

### `Promise.any` — Primeiro a Cumprir

Resolve com o primeiro valor **cumprido**. Só rejeita se **todas** as promises rejeitarem (lança `AggregateError`):

```js
const fastest = await Promise.any([
  fetch("https://server1.example.com/data"),
  fetch("https://server2.example.com/data"),
  fetch("https://server3.example.com/data"),
]);
```

> Leitura adicional: [MDN: Promise.any](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/any)

## `async` / `await`

A sintaxe `async`/`await` é **açúcar sintático sobre Promises**. Ela permite escrever código assíncrono que lê como código síncrono. Por baixo dos panos, uma função `async` retorna uma Promise, e `await` suspende a execução da função até que a Promise aguardada se resolva.

```js
// Estilo Promise:
function loadUserData(id) {
  return fetch(`/api/users/${id}`)
    .then((res) => {
      if (!res.ok) throw new Error("Not found");
      return res.json();
    })
    .then((user) => fetch(`/api/orders?userId=${user.id}`))
    .then((res) => res.json());
}

// Estilo async/await equivalente:
async function loadUserData(id) {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) throw new Error("Not found");
  const user = await res.json();
  const ordersRes = await fetch(`/api/orders?userId=${user.id}`);
  return ordersRes.json();
}
```

Regras de `async`/`await`:
- `async` sempre faz uma função retornar uma Promise
- `await` só pode ser usado dentro de funções `async` (ou no nível superior de módulos ES)
- `await` pausa apenas a **função `async` atual** — o resto do runtime JavaScript continua executando
- Se a Promise aguardada rejeitar, `await` **lança** o motivo da rejeição

> Leitura adicional: [MDN: async function](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/async_function)

## Tratamento de Erros com `try`/`catch`

Com `async`/`await`, a abordagem idiomática de tratamento de erros é `try`/`catch`:

```js
async function fetchUserProfile(username) {
  try {
    const res = await fetch(`https://api.github.com/users/${username}`);

    if (!res.ok) {
      throw new Error(`HTTP error! Status: ${res.status}`);
    }

    const data = await res.json();
    return data;
  } catch (error) {
    if (error.name === "TypeError") {
      console.error("Network failure or CORS issue:", error.message);
    } else {
      console.error("API error:", error.message);
    }
    throw error; // relançar se o chamador precisar tratar também
  } finally {
    console.log("Fetch attempt complete");
  }
}
```

### Tratando Erros Sem `try`/`catch`

Um padrão alternativo que evita aninhamento de `try`/`catch`:

```js
async function safeAsync(promise) {
  try {
    const data = await promise;
    return [null, data];
  } catch (error) {
    return [error, null];
  }
}

const [err, user] = await safeAsync(fetchUserProfile("octocat"));
if (err) {
  console.error("Failed:", err.message);
} else {
  console.log("User:", user.login);
}
```

## A Fetch API

`fetch` é a API moderna baseada em Promises para fazer requisições HTTP do navegador:

```js
// Requisição GET
const response = await fetch("https://api.github.com/users/octocat");
const user = await response.json();

// Requisição POST
const response = await fetch("https://api.example.com/items", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Authorization": `Bearer ${token}`,
  },
  body: JSON.stringify({ name: "New Item", price: 9.99 }),
});

if (!response.ok) {
  throw new Error(`HTTP ${response.status}: ${response.statusText}`);
}

const newItem = await response.json();
```

Importante: `fetch` só rejeita em **falhas de rede** (sem conexão, CORS bloqueado). Uma resposta `404` ou `500` ainda **resolve** — você deve verificar `response.ok` ou `response.status` manualmente.

> Leitura adicional: [MDN: Fetch API](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API)

## Resumo

- JavaScript é **single-threaded**: uma pilha de chamadas, uma operação de cada vez.
- O **ambiente do navegador** fornece Web APIs (timers, fetch, eventos) que operam fora do motor JS.
- O **Event Loop** coordena a pilha de chamadas com duas filas: a fila de macrotarefas e a **fila de microtarefas** (que é sempre drenada primeiro e contém callbacks de Promise).
- **Callbacks** eram o padrão assíncrono original, mas levam a código profundamente aninhado e difícil de manter.
- Uma **Promise** é um objeto que representa um valor futuro. Está sempre em um de três estados: pendente, cumprida ou rejeitada. Uma vez resolvida, é imutável.
- **Encadeamento de Promises** achata o código assíncrono retornando valores (ou novas Promises) dos handlers `.then`.
- **Combinadores de Promise**: `Promise.all` (tudo ou nada), `Promise.race` (primeiro a resolver), `Promise.allSettled` (todos, independente), `Promise.any` (primeiro a cumprir).
- `async`/`await` é açúcar sintático sobre Promises, fazendo o código assíncrono parecer código síncrono.
- Use `try`/`catch`/`finally` com `async`/`await` para tratamento limpo de erros.
- A **Fetch API** é baseada em Promises; verifique `response.ok` explicitamente já que respostas 4xx/5xx não fazem o fetch rejeitar.
