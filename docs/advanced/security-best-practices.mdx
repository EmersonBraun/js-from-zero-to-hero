# Security & Performance Best Practices

Writing correct JavaScript is not enough — production code must also be secure, performant, and free of subtle resource leaks. This module covers the most impactful frontend security threats, practical mitigation techniques, and the performance patterns every JavaScript developer should internalize.

---

## 1. Cross-Site Scripting (XSS)

XSS is the most prevalent web vulnerability. An attacker injects malicious scripts into a page that are then executed in the browser of another user, in the context of the victim's session.

### Types of XSS

**Stored XSS** — Malicious payload is stored on the server (e.g., in a database) and served to all visitors. A comment containing `<script>steal(document.cookie)</script>` that gets saved and rendered is the classic example.

**Reflected XSS** — The payload is reflected off the server in an immediate response (e.g., a search result page that echoes the query parameter as raw HTML). The attacker crafts a URL and tricks a victim into clicking it.

**DOM-based XSS** — The vulnerability lives entirely in client-side JavaScript. The script reads attacker-controlled data (URL hash, `postMessage`, `localStorage`) and passes it unsafely to `innerHTML` or `document.write`.

### Prevention

1. **Never set `innerHTML` with untrusted data.** Use `textContent` for text, `createElement` + `appendChild` for structured DOM construction.
2. **Sanitize before rendering HTML.** When you must allow formatted input, use a trusted library like [DOMPurify](https://github.com/cure53/DOMPurify).
3. **Avoid dangerous evaluation sinks:** passing user strings to `setTimeout`, dynamic function construction, `document.write()`, or `element.outerHTML`.
4. **Encode output** in the context where it appears (HTML entity encoding, URL encoding, JS string encoding).

```js
// UNSAFE
element.innerHTML = userInput;

// SAFE for plain text
element.textContent = userInput;

// SAFE for structured HTML (with DOMPurify)
element.innerHTML = DOMPurify.sanitize(userInput);
```

MDN Reference: [Types of attacks — XSS](https://developer.mozilla.org/en-US/docs/Web/Security/Types_of_attacks#cross-site_scripting_xss)

## 2. CSRF (Cross-Site Request Forgery)

CSRF exploits the browser's automatic cookie attachment. When a victim visits an attacker's page, that page silently sends a request to a site where the victim is authenticated — and the browser sends their session cookie along.

Frontend defenses:

- **Check `Origin` / `Referer` headers** server-side.
- **SameSite cookie attribute**: `SameSite=Strict` or `SameSite=Lax` prevents cookies from being sent with cross-site requests.
- **CSRF tokens**: A secret value embedded in forms and verified server-side.
- **Custom request headers**: Fetch requests with headers like `X-Requested-With: XMLHttpRequest` cannot be forged by simple HTML forms (CORS preflight blocks them for cross-origin).

```js
// Including a CSRF token in fetch requests
async function securePost(url, data) {
  const csrfToken = document.querySelector('meta[name="csrf-token"]')?.content;
  return fetch(url, {
    method: 'POST',
    credentials: 'same-origin',
    headers: {
      'Content-Type': 'application/json',
      'X-CSRF-Token': csrfToken,
    },
    body: JSON.stringify(data),
  });
}
```

## 3. Content Security Policy (CSP)

CSP is an HTTP response header that tells the browser which resource origins are trusted. Violations are blocked (and optionally reported).

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.example.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  report-uri /csp-report
```

Key directives:

| Directive | Controls |
|---|---|
| `default-src` | Fallback for all resource types |
| `script-src` | JavaScript sources |
| `style-src` | CSS sources |
| `img-src` | Image sources |
| `connect-src` | `fetch`, XHR, WebSocket |
| `frame-ancestors` | Which pages can embed this page (replaces `X-Frame-Options`) |

A strict CSP blocks inline scripts and dynamic code evaluation, which neutralizes the vast majority of XSS payloads even if an injection exists.

MDN Reference: [Content Security Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/CSP)

## 4. Memory Leaks in JavaScript

JavaScript uses garbage collection — memory is freed when there are no more references to an object. A memory leak occurs when references are retained unintentionally, preventing GC from reclaiming memory.

### Common Causes

**Forgotten event listeners** — Adding a listener to a long-lived element from a short-lived component without removing it.

```js
// Leak: listener holds reference to closure/data even after component unmounts
window.addEventListener('resize', handler);

// Fix: always remove when no longer needed
window.removeEventListener('resize', handler);
// Or: use AbortController
const controller = new AbortController();
window.addEventListener('resize', handler, { signal: controller.signal });
// Later:
controller.abort();
```

**Closures retaining large objects** — A timer callback that closes over a large data structure keeps it alive as long as the timer runs.

```js
// Leak: largeData is kept alive by the interval closure
let largeData = new Array(1_000_000).fill('x');
const id = setInterval(() => {
  console.log(largeData.length);
}, 1000);
// Fix: clearInterval(id) when done, and set largeData = null
```

**Detached DOM nodes** — A DOM element is removed from the document but a JavaScript reference keeps it (and all its children) in memory.

```js
// Leak
let detachedNode;
function createAndDetach() {
  const el = document.createElement('div');
  document.body.appendChild(el);
  document.body.removeChild(el);
  detachedNode = el; // still referenced!
}
// Fix: set detachedNode = null when done
```

**Global variables** — Accidental global assignment (missing `let`/`const`/`var`) attaches data to `window`.

```js
function leak() {
  accidentalGlobal = 'still alive'; // implicit global
}
// Fix: strict mode throws ReferenceError on undeclared assignment
```

**WeakMap** — Use `WeakMap` to associate data with objects without preventing GC.

```js
const cache = new WeakMap();

function process(obj) {
  if (cache.has(obj)) return cache.get(obj);
  const result = expensiveCompute(obj);
  cache.set(obj, result); // won't prevent obj from being GC'd
  return result;
}
```

MDN Reference: [Memory management](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Memory_management)

## 5. Event Delegation Pattern

Event delegation attaches a **single listener to a parent element** and handles events from many children via event bubbling. This is more performant (fewer listeners, no re-registration for dynamic children) and naturally avoids a category of memory leaks.

```js
// Without delegation — a listener per item
document.querySelectorAll('.item').forEach(item => {
  item.addEventListener('click', handleClick);
});

// With delegation — one listener, works for dynamic children too
document.getElementById('list').addEventListener('click', (event) => {
  const item = event.target.closest('.item');
  if (!item) return;
  handleClick(item);
});
```

Benefits:
- Works for dynamically added children (no re-registration needed).
- Drastically fewer listeners for large or dynamic lists.
- Single `removeEventListener` call to clean up.

MDN Reference: [Event delegation](https://developer.mozilla.org/en-US/docs/Learn/JavaScript/Building_blocks/Event_bubbling#event_delegation)

## 6. Debounce Pattern

Debounce delays execution until a function has **stopped being called** for a specified wait period. If the function is called again before the wait expires, the timer resets.

Use cases: search-as-you-type, form validation on input, window resize handling.

```js
function debounce(fn, wait) {
  let timer;
  return function(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => {
      fn.apply(this, args);
    }, wait);
  };
}

const debouncedSearch = debounce((query) => {
  fetch(`/api/search?q=${encodeURIComponent(query)}`);
}, 300);

searchInput.addEventListener('input', (e) => debouncedSearch(e.target.value));
```

**Leading-edge debounce** — fires immediately on first call, then blocks until quiet:

```js
function debounceLeading(fn, wait) {
  let timer;
  return function(...args) {
    if (!timer) fn.apply(this, args);
    clearTimeout(timer);
    timer = setTimeout(() => { timer = null; }, wait);
  };
}
```

MDN Reference: [setTimeout](https://developer.mozilla.org/en-US/docs/Web/API/setTimeout)

## 7. Throttle Pattern

Throttle ensures a function is called **at most once per interval**, regardless of how many times it is triggered. Unlike debounce, it guarantees periodic execution during sustained activity.

Use cases: scroll event handlers, mouse move tracking, rate-limiting API calls.

```js
function throttle(fn, interval) {
  let lastCall = 0;
  return function(...args) {
    const now = Date.now();
    if (now - lastCall >= interval) {
      lastCall = now;
      return fn.apply(this, args);
    }
  };
}

const throttledScroll = throttle(() => {
  updateScrollProgress();
}, 100); // at most 10 times per second

window.addEventListener('scroll', throttledScroll);
```

| Pattern | Fires when | Best for |
|---|---|---|
| Debounce | Activity stops | Search input, resize completion |
| Throttle | At regular intervals | Scroll, mousemove, game loops |

## 8. Input Sanitization

Never trust user input. Sanitize at every boundary.

```js
// HTML entity encoding — safe for inserting text into HTML contexts
function escapeHTML(str) {
  return String(str)
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#x27;');
}

// URL parameter sanitization
function buildSearchURL(query) {
  const url = new URL('https://example.com/search');
  url.searchParams.set('q', query); // URL API handles encoding
  return url.toString();
}

// Numeric input validation
function sanitizeAge(input) {
  const n = parseInt(input, 10);
  if (Number.isNaN(n) || n < 0 || n > 150) return null;
  return n;
}
```

Key rules:
- Sanitize **at the point of use**, not only at input.
- Use the **right encoding for the context** (HTML, URL, JSON, SQL — each differs).
- Prefer structured APIs (`URLSearchParams`, `JSON.stringify`) over manual string building.
- Allowlist valid values where possible instead of trying to blocklist invalid ones.

## 9. Secure Coding Practices

**Avoid dynamic code execution** — Passing user-controlled strings to `setTimeout`, `setInterval`, or other dynamic evaluation mechanisms executes arbitrary code and bypasses all CSP and static analysis protections. Use callback functions instead of string arguments.

**Use strict mode** — Catches undeclared variables, prevents `this` coercion, and disables legacy dangerous features.

**Validate data shape** — When consuming external data (APIs, `postMessage`, `localStorage`), validate the structure before use.

```js
window.addEventListener('message', (event) => {
  // Always verify origin
  if (event.origin !== 'https://trusted.example.com') return;

  // Validate shape
  const { type, payload } = event.data ?? {};
  if (typeof type !== 'string' || !payload) return;

  handleMessage(type, payload);
});
```

**Subresource Integrity (SRI)** — Verify third-party scripts have not been tampered with:

```html
<script
  src="https://cdn.example.com/lib.js"
  integrity="sha384-<hash>"
  crossorigin="anonymous"
></script>
```

**Avoid storing sensitive data in `localStorage`** — It is accessible to any JavaScript on the page. Prefer `HttpOnly` cookies for session tokens.

MDN Reference: [Web security](https://developer.mozilla.org/en-US/docs/Web/Security)

## Summary

- **XSS** is prevented by avoiding unsafe sinks (`innerHTML`, dynamic code execution), sanitizing untrusted HTML with DOMPurify, and using `textContent` for plain text output.
- **CSRF** is mitigated by `SameSite` cookies, CSRF tokens, and verifying request origins server-side.
- **Content Security Policy** is a declarative allowlist that blocks unauthorized script sources and neutralizes most XSS payloads at the browser level.
- **Memory leaks** arise from forgotten event listeners, timer closures, detached DOM nodes, and accidental globals. Use `removeEventListener`, `AbortController`, `clearInterval`, and `WeakMap` to prevent them.
- **Event delegation** attaches one listener to a parent rather than many listeners to children — more performant and inherently correct for dynamic content.
- **Debounce** delays execution until activity stops; **throttle** limits execution rate during sustained activity. Both are essential for high-frequency event handlers.
- **Input sanitization** must be context-aware: HTML entity encoding, URL encoding, and structural validation serve different purposes and are not interchangeable.
- **Secure coding** means validating `postMessage` origins, avoiding dynamic code evaluation with user input, using strict mode, preferring `HttpOnly` cookies for tokens, and applying Subresource Integrity for third-party scripts.
