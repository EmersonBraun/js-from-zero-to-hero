Closures

What Are Closures?​

A closure is one of the most fundamental — and most misunderstood — concepts in JavaScript. At its core, a closure is the combination of a function and its lexical environment: the set of variables that were in scope when the function was created, which it retains access to even after the outer scope has finished executing.

MDN defines it this way:

"A closure is the combination of a function bundled together (enclosed) with references to its surrounding state (the lexical environment). In other words, a closure gives you access to an outer function's scope from an inner function."

— MDN: Closures

To understand closures, you first need a solid grasp of lexical scope and how the scope chain works.

Lexical Scope and the Scope Chain​

JavaScript uses lexical scoping (also called static scoping): a function's scope is determined by where the function is written in the source code, not where it is called from.

const x = 10;

function outer() {
  const y = 20;

  function inner() {
    const z = 30;
    console.log(x, y, z); // 10, 20, 30
  }

  inner();
}

outer();

When inner runs, the JavaScript engine looks up variable x by walking the scope chain:

  1. Check inner's own scope → not found
  2. Check outer's scope → not found
  3. Check the global scope → found: x = 10

This chain is established at the time the function is defined, not when it is called. That is the essence of lexical scope.

The [[scope]] Internal Slot​

Every function object in JavaScript has an internal property called [[scope]] (sometimes written as [[Environment]]). This hidden slot holds a reference to the environment record — the actual scope — in which the function was created.

When a function is invoked, a new execution context is created. That context's outer environment pointer is set to whatever was stored in [[scope]]. This is what forms the scope chain at runtime.

Further reading: MDN: Scope

The "Backpack" Mental Model​

A useful mental model for closures is the backpack (or "closed-over variable environment", COVE):

When a function is created inside another function, the inner function "packs" a copy of the surrounding variables into an invisible backpack strapped to its back. No matter where the function travels — even after the outer function has returned and its execution context has been popped from the call stack — the backpack is always there.

function makeCounter() {
  let count = 0; // this gets packed into the closure backpack

  return function () {
    count++;
    return count;
  };
}

const counter = makeCounter();
console.log(counter()); // 1
console.log(counter()); // 2
console.log(counter()); // 3

makeCounter has long since returned, yet count is still alive. Why? Because the returned function holds a live reference to the variable count inside its closure. The garbage collector cannot reclaim count while that reference exists.

How JavaScript Manages Closure Memory​

When the JavaScript engine creates a function that closes over variables, those variables are stored on the heap rather than on the stack. Stack frames are popped away when a function returns, but heap allocations persist as long as something holds a reference to them.

The closed-over variable environment is essentially an object on the heap:

Heap:
  ClosureEnv { count: 3 }
      ↑
  counter function's [[scope]] points here

This means closures do consume memory. For long-lived applications, it is important not to accidentally retain large objects in closures when they are no longer needed.

Further reading: MDN: Memory Management

Practical Closure Patterns​

1. Factory Functions​

A factory function is a function that returns a new, customized function. Closures make this powerful:

function multiplier(factor) {
  return (number) => number * factor; // factor is closed over
}

const double = multiplier(2);
const triple = multiplier(3);

console.log(double(5));  // 10
console.log(triple(5));  // 15

Each call to multiplier creates a fresh closure with its own factor. double and triple are completely independent.

2. Private Variables (Module Pattern)​

JavaScript did not have native private class fields until ES2022. Before that, closures were the idiomatic way to achieve data encapsulation:

function createBankAccount(initialBalance) {
  let balance = initialBalance; // truly private — not accessible from outside

  return {
    deposit(amount) {
      balance += amount;
      return balance;
    },
    withdraw(amount) {
      if (amount > balance) throw new Error("Insufficient funds");
      balance -= amount;
      return balance;
    },
    getBalance() {
      return balance;
    },
  };
}

const account = createBankAccount(100);
account.deposit(50);       // 150
account.withdraw(30);      // 120
console.log(account.balance); // undefined — not directly accessible!

3. Memoization​

Memoization is an optimization technique that caches the results of expensive function calls. Closures are perfect for storing the cache:

function memoize(fn) {
  const cache = new Map(); // closed over — lives as long as memoized function does

  return function (...args) {
    const key = JSON.stringify(args);
    if (cache.has(key)) {
      console.log("Cache hit!");
      return cache.get(key);
    }
    const result = fn.apply(this, args);
    cache.set(key, result);
    return result;
  };
}

function slowFibonacci(n) {
  if (n <= 1) return n;
  return slowFibonacci(n - 1) + slowFibonacci(n - 2);
}

const fastFibonacci = memoize(slowFibonacci);
console.log(fastFibonacci(40)); // computed
console.log(fastFibonacci(40)); // Cache hit! — instant

4. Debounce​

Debouncing delays execution of a function until after a specified period of inactivity. This is essential for performance when handling high-frequency events like input, resize, or scroll:

function debounce(fn, delay) {
  let timeoutId; // closed over — persists between calls

  return function (...args) {
    clearTimeout(timeoutId);
    timeoutId = setTimeout(() => {
      fn.apply(this, args);
    }, delay);
  };
}

const handleSearch = debounce((query) => {
  console.log("Searching for:", query);
}, 300);

// Only fires once, 300ms after the user stops typing
document.querySelector("input")?.addEventListener("input", (e) => {
  handleSearch(e.target.value);
});

timeoutId is a private variable living inside the closure. Each call to the returned debounced function shares the same timeoutId, allowing the previous timeout to be cancelled.

Further reading: MDN: setTimeout

5. Iterators​

Closures can create stateful iterators without classes:

function range(start, end, step = 1) {
  let current = start;

  return {
    next() {
      if (current <= end) {
        const value = current;
        current += step;
        return { value, done: false };
      }
      return { value: undefined, done: true };
    },
  };
}

const iter = range(1, 5);
console.log(iter.next()); // { value: 1, done: false }
console.log(iter.next()); // { value: 2, done: false }
console.log(iter.next()); // { value: 3, done: false }

Further reading: MDN: Iterators and Generators

The Classic Loop Trap​

One of the most infamous closure bugs in JavaScript:

// BROKEN: using var
for (var i = 0; i < 3; i++) {
  setTimeout(function () {
    console.log(i); // prints 3, 3, 3 — not 0, 1, 2!
  }, 1000);
}

Why? Because var is function-scoped, not block-scoped. All three callbacks close over the same i variable. By the time the timeouts fire, the loop has finished and i is 3.

Solution 1: Use let

for (let i = 0; i < 3; i++) {
  setTimeout(function () {
    console.log(i); // 0, 1, 2 ✓
  }, 1000);
}

let is block-scoped. Each loop iteration creates a new binding of i, so each callback closes over a different variable.

Solution 2: IIFE (for older codebases)

for (var i = 0; i < 3; i++) {
  (function (j) {
    setTimeout(function () {
      console.log(j); // 0, 1, 2 ✓
    }, 1000);
  })(i);
}

The IIFE creates a new scope on each iteration, capturing the current value of i as the parameter j.

Further reading: MDN: let

The IIFE Pattern​

An Immediately Invoked Function Expression (IIFE) is a function that is defined and called at the same time:

(function () {
  const privateData = "I am not global";
  console.log(privateData);
})();

// privateData is not accessible here

IIFEs were the backbone of the module pattern before ES modules existed. They allowed libraries to expose only a public API while keeping internal state private:

const Calculator = (function () {
  let history = []; // private

  function add(a, b) {
    const result = a + b;
    history.push(`${a} + ${b} = ${result}`);
    return result;
  }

  function getHistory() {
    return [...history]; // return a copy to prevent mutation
  }

  return { add, getHistory }; // public API
})();

Calculator.add(2, 3); // 5
Calculator.getHistory(); // ["2 + 3 = 5"]

Project: Auto Text Effect​

This project uses closures to manage the animation state of a typing effect — each character reveal is driven by a setTimeout callback that closes over the full text string and the current index.

How Closures Power It​

The core mechanism:

function typeWriter(element, text, speed = 50) {
  let index = 0; // closed over by the tick function

  function tick() {
    if (index < text.length) {
      element.textContent += text[index];
      index++;
      setTimeout(tick, speed); // tick closes over index and text
    }
  }

  tick();
}

tick is a recursive function that closes over index and text. Each call to typeWriter creates an independent closure, so multiple animations can run simultaneously without interfering.

typeWriter(el, "Hello!", 50, () => console.log("Done!"));

Summary​

  • A closure is a function paired with its lexical environment — the variables in scope when it was defined.
  • JavaScript functions carry their [[scope]] with them wherever they go via an internal slot.
  • Closed-over variables live on the heap, not the stack, which is why they outlive their enclosing function's execution.
  • The backpack mental model: inner functions carry their surrounding variables as an invisible backpack.
  • Key patterns enabled by closures: factory functions, private state, memoization, debounce, iterators, and currying.
  • The classic loop trap occurs because var shares one binding across all loop iterations; fix it with let or an IIFE.
  • IIFEs were the original module pattern — they create a private scope and expose only a public API.
